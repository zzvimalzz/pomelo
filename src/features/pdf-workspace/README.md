# PDF workspace

A window that reads PDFs, one tab for each. It opens from the tray menu (**Open a PDF…**), from Explorer's right-click entry **Open in Pomelo** on a `.pdf`, from the Open wheel and from the command line (`--open=<path>`), and shows the document with pdf.js. It works with no engine installed and sends nothing over the network.

## How it works

1. `src/app/main.js` creates the workspace with `createWorkspace(deps)` and calls `registerIpc()` at start-up. `main.js` requires only `index.js`; `workspace.window.js` is loaded the first time a PDF is opened.
2. `open(paths)` opens each path in `documents.js`: one read handle that stays open until its tab is closed, a random 32-byte token, the file's name and size. Calls are served one at a time. A file that cannot be read gets a notice in the corner of the screen (`notify`), once for the whole call. A file that is open already (the same path, whatever its case) is shown again, not opened twice, and at most ten are open at once (`Too many PDFs open`, `Close one to open another.`). Each file that opens goes to the front of `pdfRecent`, up to ten full paths; `recent.js` keeps that list, and the Open dialog starts in the folder of the newest one whose folder is still there. While a window is open a call sends the new documents to its page with `pdfws:opened` and brings the window to the front.
3. `workspace.window.js` makes the window (below) and loads `ui/workspace.html`. The page asks `pdfws:state` which documents it was opened for, makes a tab for each and shows the first (Tabs, below).
4. `ui/viewer.js` opens a tab's document with pdf.js. The page never gets a path and never asks for the whole file: pdf.js is given a `PDFDataRangeTransport` whose `requestDataRange` calls `pdfws:read(token, begin, end)`, and the main process reads that range from the held handle. `loadOptions()` is the one place the `getDocument` options are set. A request larger than 4 MiB is read in pieces and handed to pdf.js as one, because pdf.js answers one request with one call.
5. `PDFViewer` draws the pages as the user scrolls and fits the first one to the window. A fit (Fit page or Fit width) is applied again when the window is resized; a zoom the user chose is left alone.
6. A password-protected file makes pdf.js ask for a password. `ui/dialogs.js` shows one card for the whole open, headed by the file as a PDF icon with a lock on it (the icon is drawn by the wheel's `wheel-icons.js`), with an eye button that shows or hides what is typed, and `viewer.js` gives each answer to pdf.js and gives up after five wrong ones or on Cancel. The button is off until something is typed. While pdf.js checks a password the field and the button rest (the button shows a spinner) and Cancel stops the check. A wrong password is answered in the same card: the field turns red and shakes once, **Wrong Password** appears under it, what was typed stays selected, and the button reads **Try Again**. The card is removed, and its field emptied, when the open ends. When it gives up, the page says the file is password-protected and its **Unlock** button runs the whole open again, with a fresh count. Only once pdf.js has accepted a password does the page send it to the main process with `pdfws:unlock`; `documents.js` keeps it as a `Buffer` in a private map, away from the document's record, and overwrites it with zeros when the window closes. The page forgets it at once, and the card's field is emptied before the card goes.
7. `ui/dock.js` builds the dock in the document area once pdf.js has the page count (below). `ui/focus.js` runs focus reading (below). `ui/keys.js` holds every shortcut in one table.
8. `ui/comments-margin.js` listens for `annotationlayerrendered`, reads the page's annotations from pdf.js and draws a marker for each comment (below). It reads only the pages pdf.js has drawn, so a large file is never scanned for them.
9. `ui/sidebar.js` runs the left panel and its Pages and Outline tabs, building a tab the first time it is shown; `ui/thumbs.js` draws the thumbnails and `ui/outline.js` builds the bookmarks (below).
10. `ui/search.js` builds the find bar and gives pdf.js's `PDFFindController` (made in `viewer.js` and handed to the viewer) its questions; `ui/results.js` lists the hits in the Search tab of the panel on the right, `ui/ticks.js` marks them beside the scroll bar and `ui/select.js` lets a selection start on empty paper (below).
11. `ui/side.js` runs the panel on the right with its Search and Links tabs; `ui/results.js` fills the Search tab and `ui/linklist.js` the Links tab (below).
12. `ui/colours.js` draws the pages in the colours the user chose, and `pdfws:state` hands the page the view it was last left in (below).
13. `src/ui-shared/tabs.js` draws the row of tabs and `ui/workspace.js` keeps the tabs and shows the one chosen (below).
14. `ui/organise.js` is the Pages tool: a button in the dock and a grid of every page that takes the place of the reading view (below). `ui/split.js` and `ui/addfiles.js` are the cards its bar opens to split the document into files and to add other files to it.
15. The **More** button in the dock opens a menu of two items, **Convert to…** and **Save a copy**. `ui/dock.js` draws it and `ui/workspace.js` gives it its items; `ui/dialogs.js` has the card of formats (Converting, below).

## Changes, versions and Save

A change becomes a revision, a whole PDF file in a session folder. The Description fields, the Pages grid and the markup tools make them. There are two ways in: the page's `workspaceApi.putRevision(token, bytes)`, for pdf.js's `saveDocument()` bytes, and `workspaceApi.apply(token, ops)`, a list of changes the PDF engine makes (below).

1. `documents.js` keeps a chain of revisions for each document (`revisions.js`, no Electron). Revision 0 is the file, read through the handle opened with the document. The first change makes the session folder (`makeTempDir('pdfws')` in the temp folder), copies the file into it with `fs.copyFile`, checks before and after the copy that the file still has the identity recorded at open (its NTFS file index, size and time of last change), and lets go of the file's handle: from then on revision 0 is the copy, and Save is the only thing that touches the user's file again. A file another program changed or deleted stops the change with `changed` and nothing is left behind.
2. `pdfws:put-revision` takes the whole file as a `Uint8Array` (it must hold `%PDF-` in its first kilobyte) and refuses one over `NO_ENGINE_SAVE_LIMIT`, 100 MB, with `too-large`: pdf.js's `saveDocument()` holds about four times the file in the renderer, which the limit keeps under 1.5 GB. A free-space check (`size + 64 MB`) comes before every revision, on the temp drive (`no-space`). At most 30 revisions are kept, and their total size stays within `max(2 GB, 4 × the file)` capped at half the free space of the temp drive: the oldest after the first go, and the revision on show never does. A revision that is being read is let go of when the read ends.
3. `pdfws:apply` takes a token and a list of changes and, with the PDF engine, makes the next revision from the one on show. `ops.js` (no Electron) holds the closed list of operations (`annot.add`, `pages.rotate`, `pages.delete`, `pages.move`, `pages.insert`, `pages.blank`, `pages.extract`, `meta.set`), the keys and values each takes and its kind (`direct` edits in place, `annotate` adds markup to the end of the file, `rewrite` writes the file whole), and `check(list)` returns a copy that holds only those keys or throws, so the page cannot send a key the schema has not named. Then `documents.apply` checks for room (`2 ×` the file `+ 64 MB` on the temp drive, `no-space`), takes the snapshot if this is the first change, writes the list to `ops-N.json` in the session folder, and runs `python/pdf_edit.py <current revision> <next revision> <list>` through `runPdfTool` (handed in by the app). Python reads and writes only files in the session folder. The helper's output is adopted as the next revision only if it exits cleanly; any failure removes the half-written file and the list, and rejects with the helper's one-line reason. If the document has a password (`pdfws:unlock`), it goes to the helper on its standard input as one line of JSON and nowhere else. Closing the document, or quitting, kills a helper that is still running. The page is told `{ stop: 'no-engine' }`, `'cancelled'` or `'failed'` (the last also shows **Can't make this change** with the helper's reason in the corner notice) and the new state through `pdfws:changed` with `reload`. Pages in a list are counted in the document as the changes before them left it.
4. `pdfws:undo` and `pdfws:redo` step one revision and answer `null` at the ends. Every change of state is sent to the page with `pdfws:changed` (the document's token, name, size and whether it has changes, and `reload` when the pages must be read again). `ui/workspace.js` then redraws the dot and the Save button and, for undo, redo and reload, opens the tab's document again at the zoom, layout and place it was left in. A password-protected document asks for its password again then.
5. A document has changes while the revision on show is not the one last saved, or the file as opened. A revision made from another by `meta.set` alone, or by page changes alone, counts as that other one when the document is the same again: `documents.js` gives such a revision its `base`, its `meta` (the four texts; a revision that only changed pages takes them from the one it came from, `metaFrom`) and its `layout`, where every page is now (`arrange()` in `ops.js`: the page it was and the degrees it was turned, or nothing when the pages are as the document began). The engine's answer about any revision gives it its `meta` too. So typing a Title back as the file had it, turning a page and turning it back, moving a page and moving it back, or undoing to the saved revision, leaves nothing to save and takes the dot and the Save button away. Before the engine has read a file's texts, a change typed back still counts, and a document of more than 50 000 pages is not followed this way. The layout is built from the page count the helper prints (`{"pages": n}`, the pages of the file it was given). A document with changes shows an accent dot after its name (after the tab's name when there are tabs) and a **Save** button at the right of the title row; **Ctrl+S** saves, **Ctrl+Shift+S** saves a copy. The first Save of a tab asks once, **Replace the original?** with Cancel, Save a copy and Replace. After a Save, **Saved** shows in green beside the name for 1.4 s. `pdfws:save` replaces the file with `replaceFile` (below) and takes the file's new identity; `pdfws:save-as` asks for a name in a Save dialog that starts in the file's folder with `<name> (edited).pdf` made unique, and writes there the same way, leaving the file it came from as it was. Called with `openCopy` (the page sends it unless the window or the tab is closing), it then opens the copy in a tab (`add`; a copy saved over a file that is open in another tab reads that tab again) and answers `copied`, and the page closes the document the copy came from, with its changes. Saving over the file itself is a Save. A file another program changed since it was opened is never saved over: the page asks `<name> was changed by another program.` with Cancel, Reload (read the file again, dropping the changes) and Save a copy.
6. Why a save stopped is said in the corner notice, **Can't save**, with `<name> is open in another program. Close it there, or save a copy.`, `<name> is read-only. Save a copy instead.`, `There is not enough free space on <drive> to save <name>.` or `Saving changes to a file this large needs the PDF engine.`; the page is given only the reason.
7. Closing a tab with changes asks `Save changes to <name>?` (Cancel, Don't save, Save). Closing the window, and quitting Pomelo, ask the same about each document with changes in turn: the window's `close` is held back, the page asks, and `pdfws:close-window` lets it go when none was cancelled. Closing a tab or the window lets go of every revision's handle and removes the session folder; session folders older than a day that a crash left are removed when Pomelo starts.

`replaceFile(src, target, expected)` in `src/shared/node/fs.js` does the replacing. It stops with `changed` when the target's identity is not `expected` (or, with `expected` null, when something is there), `read-only` or `no-space`; copies the revision beside the target as `.<name>.pomelo-<8 hex>.tmp`, flushes it and checks its size and `%%EOF`; and puts it in place with .NET's `File.Replace` (the Windows call `ReplaceFileW`) through PowerShell, started with its window hidden (`windowsHide` and `-WindowStyle Hidden`, so no console shows) and with the two paths in environment variables. A rename over the file fails while any handle on it is open, Pomelo's own included; `File.Replace` works with one open and keeps the file's permissions, creation time and its `Zone.Identifier` stream (the downloaded-file mark). A sharing violation is tried again three times over about 350 ms and then is `locked`. Any failure leaves the file as it was and removes the temporary file. Save costs about 0.3 s more than a rename for starting PowerShell.

## Tabs

With one PDF the title row shows its name. With more it shows a row of tabs in the same place: the tab on show is raised, a cross appears on hover and on the tab on show, and a long name is cut with its full name in the tooltip. The row shares the room down to 96 px a tab, about a dozen letters of a name; with more tabs than that it scrolls sideways, by the mouse wheel too, keeps the tab on show in view and fades on the side that has more. The title row is a grid whose outer columns are as wide as their buttons (`minmax(max-content, 1fr)`) with 12 px between columns, so the tabs or the name stay centred while there is room, and a button added on either side, Save included, takes its room from the tabs instead of covering them. A tab selects with a click or with Left, Right, Home and End along the row (one tab stop, the tab on show), and closes with its cross or with Delete. The row is `role=tablist`, the tabs `role=tab`.

There is one `PDFViewer` for the window. A tab keeps its pdf.js document, which it opens the first time it is shown (ten files opened together cost one document until the others are clicked), but only the tab on show has drawn pages: choosing another sets that tab's document into the viewer with `setDocument`, which destroys the drawn pages of the one left. The tab left keeps its zoom, layout and scroll position and gets them back when it is shown again; a tab shown for the first time starts from the remembered view. The dock is the exception while the Pages grid is waiting for a change to be read back: it stays up, so it does not drop out and slide in again after every edit. Every module that holds something of the document (the dock, the panels, the find bar, the list of links, the markers, the colour layers) clears it on pdf.js's `pagesdestroy` and builds it again on `pagesinit`, so none needs to know about tabs. The find bar and its hits are cleared when the tab changes; the left panel keeps its place and tab.

A file that fails (not a PDF, or locked and not unlocked) says so in its own tab; coming back to it shows the same message, and **Unlock** runs the open again. Closing a tab sends `pdfws:close`: the main process closes the file's handle and forgets its password, and the window closes with the last tab. Closing the window closes every file.

A PDF dropped on the window opens in a new tab. The preload reads the drop (`webUtils.getPathForFile`) and sends the paths on with `pdfws:drop`, so the page never sees a path, and it ignores a drop that a script made up. The main process keeps only absolute paths ending in `.pdf`; a drop with none says `PDF files only`.

## The dock

A glass bar at the bottom centre of the document area, with two groups, the tools (Highlight, Draw, Text, Pages) and the More button (see Converting). Under 440 px of room it also drops Zoom out and Zoom in and the line before Pages. **Pages**: Previous, a page box (as wide as its digits, so the page and the total sit in the middle between the arrows) that shows the current page and, with a number and Enter, goes to that page (a number past the end goes to the last page, anything else is ignored), and Next. **Zoom**: Zoom out, the zoom value and Zoom in. The value reads `Fit page`, `Fit width` or a percentage, and opens the View menu: Zoom (`Fit width`, `Fit page`, `Actual size`) Layout (`Continuous`, `Two pages side by side`, which sets `spreadMode`) and Page colour (`Original`, `Sepia`, `Dark`, `Custom colours…`; see Page colours). The menu closes on a choice, on a click elsewhere or on Esc, and Up and Down move between its items. Zoom buttons and keys step by pdf.js's own steps round the middle of the view. Ctrl and the mouse wheel zoom wherever the pointer is in the window, round the pointer when it is over the document area: the listener is on `window`, turns add up and every 100 (one mouse notch) is a step, so quick turns are never dropped and a trackpad pinch, which sends many small ones, still moves in steps. pdf.js is given the point to hold still in the coordinates of the well, which is the scroller's offset parent. While the Pages grid is up the zoom buttons size its pages instead (the value then shows the thumbnail size as a percentage of 160 px and does not open the menu), and the page buttons and box move the grid's focus; `organise.js` answers `zoom`, `go` and `step` with `false` when the grid is not up, so the dock falls back to the document.

The dock stays where it is while the document scrolls. A round 36 px button stands just past its end (below a column) and folds it away: the bar slides off the edge it stands at, and 260 ms in the button glides to the middle of the dock's place; pressed again, the button moves aside first and the bar slides back 180 ms later. The Pages grid's bar of actions goes and comes back with it, on the same curves and wait, sliding toward the edge the dock goes to (down from the bottom, up from the top, down from a side) as it fades, and passes clicks through while it is away. With reduced motion neither slides: the folded rules name their own transitions, so the reduced-motion block turns them off by name. A folded dock is `inert`, so Tab and the pointer pass it by. The bar (`.dock`) and its button sit in one holder (`.dockwrap`) that carries the place, the drag and the focus-reading slide, so the button is placed by CSS alone and follows the bar through a drag, a resize and focus reading. The fold is not kept: a new window starts with the dock showing. The dock is nearly opaque (`--dock`, 97 %) and `user-select: none`, so highlighted text under it does not show through and nothing can be selected from it. A pill in the top middle of the pages names the page for a moment when the page changes while the dock is folded or in focus reading. Buttons do not take the focus, so keys keep acting on the document. Page Down, Page Up and the arrows only turn pages in focus reading; otherwise the focused scroller does what it does.

## Where the dock stands

The grip at the start end of the dock (a dotted texture; **Drag to move**) is held and dragged. While it is dragged the dock follows the pointer and four dashed places are marked, the one nearest the pointer in the accent: the middle of the bottom edge (the default), top, left and right. Each place is the size of the dock that lands there (`sizes()` measures the dock as a row and as a column with transitions held off, then puts the grid's scroll back), and the dragged dock keeps 16 px from every edge of the document area. On release the dock eases to that place; at the left and right it is a column 76 px wide, its page arrows point up and down (they scroll), the page and the total are stacked without the slash, and its View menu opens beside it; at the top the menu opens below. With the grip focused the arrow keys move it the same way. `dock-place.js` does this and `well[data-dock]` carries the side, which `workspace.css` reads; the fold button, the edge handle, the page pill and focus reading all follow it. The dock eases to its new place in 480 ms while its button stays fixed to it. A click on the grip without a drag changes nothing. When the document area is under 440 px wide (both side panels open in a small window) the Pages label is dropped and the fold button stands over the end of a dock lying flat instead of beside it, so neither runs off the edge.

The place is kept in `pdfView.dock` and has no time limit. The page asks the main process to keep it with `pdfws:dock`, which accepts only `bottom`, `top`, `left` or `right`; a stored value that is anything else opens at the bottom.

## The side panel

The button at the left of the title row (**Pages and outline**) slides a panel open beside the document area, which gives up that room; pressed again it slides shut. The panel is 214 px wide, and a grip on its right edge (a faint bar on hover, `col-resize`) sets any width from 214 to 320 px: dragged with the pointer, or with Left and Right on the focused grip in steps of 16 px. The width follows the pointer as it moves and is kept for as long as the window is open, shut or not. A switch at the top of the panel, **Pages** and **Outline**, chooses what it shows; the tab in use is the one the panel opens on again. Whether the panel is open, its tab and its width are remembered for the next window (see Page colours and the remembered view); a window that starts with the panel open shows it at once, without the slide.

### Pages

 The panel is part of the glass, with no frame of its own. It shows one entry for every page: a white sheet with the page number under it. The sheet is the panel's width less 94 px (120 px at the narrowest, 226 px at the widest), and a page taller than twice that width is shrunk to twice its width in height. The page in view has an accent outline and the panel scrolls to keep it in view; a click on an entry goes to that page and returns the keys to the document. Only the current entry is in the Tab order. The button is off until pdf.js has the page count and shows an accent tint while the panel is open.

Nothing is built until the panel is first opened. Entries are plain buttons whose sheets are sized by CSS from the page's height over width (the `--r` of the button) and the `--sheet` width of the panel, so a drag resizes thousands of them without any script; an `IntersectionObserver` on the panel's scroll area (300 px of margin above and below) asks `thumbs.js` for the pages that come into view and lets go of the ones that leave. Shut, the panel's list is `hidden`, so no thumbnail is asked for. `thumbs.js` draws the pages that are asked for one at a time, in the order they were asked, with a pause between two so the main view is never starved; a page that leaves the view while it is being drawn is cancelled. Each is drawn at the sheet's width at the screen's pixel density (at most twice) into one scratch canvas and kept as an `ImageBitmap`. Up to 300 bitmaps are kept, fewer when they are large (110 MB in all, so 94 at the widest panel on a screen at twice the density), the least recently shown dropped and closed. While the grip is dragged the sheets and the pictures on them are scaled by CSS; when it is let go the bitmaps are dropped and the pages in view are drawn again at the new width, and a page that is still kept is painted at once when it comes back into view. A thumbnail's canvas lives only while its entry is near the view, so the page count never decides how many canvases exist. In focus reading the panel floats over the left edge of the pages (glass, below the dock and the title row) instead of pushing them, so the pages keep the whole width and do not move when it opens or shuts; the title row's button, which returns with the top edge, opens and shuts it there too, and it stays as it was when focus reading ends. Only the Pages button is tinted when on: the Focus reading button shows its state by its icon and tooltip alone.

### Outline

`outline.js` asks pdf.js for the document's bookmarks the first time the Outline tab is shown and draws them as a tree. A bookmark with children has a chevron and is open unless the file marks it closed (a negative `/Count`, as pdf.js reads it); the children of a bookmark are built when it is first opened, so a long outline costs only what is shown. A click on a bookmark goes to its destination with `linkService.goToDestination`, which also handles named destinations; pdf.js then moves the focus to the text layer of the page it lands on, inside the document area, so the keys keep acting on the document. A click on the chevron, or on a bookmark that has children but no destination, opens or closes it. A bookmark that links to a web page or runs an action has no destination here: it is shown and does nothing. Bold and italic bookmarks are drawn bold and italic; the colour a file gives is ignored. A document with none shows **This document has no bookmarks**.

The tree is a keyboard tree: one bookmark is in the Tab order, Up and Down move between the visible ones, Right opens a closed bookmark and then goes to its first child, Left closes an open one and then goes to its parent, Enter and Space do what a click does. The keys are used up by the tree, so in focus reading they do not turn pages. Titles are text from the file and go in with `textContent` only.

## Text and find

The pages have pdf.js's text layer, so text can be selected with the pointer and copied with Ctrl+C; pdf.js lays the spans out in the file's reading order and puts a line break between lines, so a selection over two lines copies as two lines.

`select.js` lets a selection start where there is no text. pdf.js's text layer starts one only on a line of text (its end-of-content block is `user-select: none`), so a press on bare text layer (the margin, an indent, the space below the last line) is taken over: the nearest line is found from the boxes of the layer's text nodes, read once per drag and kept relative to the layer, and `setBaseAndExtent` carries the selection from there to wherever the pointer is. The point is put at the start of the nearest line when it is left of it, at the end when it is right of it, and between its letters when it is over it. A drag past the top or bottom edge of the document area scrolls on in steps every 40 ms. A press on text, a double or triple click and a Shift press are left to the browser.

The second button at the left of the title row (**Find**, Ctrl+F) opens a bar at the top middle of the document area: a field (`Find in document`), the count, **Aa** (Match case), **W** (Whole words), Previous (Shift+Enter), Next (Enter) and Close (Esc). Ctrl+F opens it from anywhere with the focus in the field and its text selected; the button is tinted while the bar is open. `search.js` does no matching of its own: every change in the field, every toggle and every Enter sends pdf.js's event bus a `find` event (the query, the two options, `highlightAll` always on and the direction) and shows what `updatefindmatchescount` and `updatefindcontrolstate` answer, as `n of m` or `No results`. pdf.js reads the text of the pages in turn, so the total grows while it works; typing is answered 250 ms after the last key. A phrase that runs over a line break is found because pdf.js matches over the page's whole text with its own rules (spaces, line ends, case, punctuation, accents). Every hit on the pages in view is marked in the Pomelo pink (`--found` in `workspace.css`, which sets pdf.js's `--highlight-bg-color`) and the one in view is a plain yellow highlight (`--found-now`, `--highlight-selected-bg-color`), so it stands out from the rest. pdf.js scrolls a hit it steps to with `scrollIntoView`, and `workspace.css` gives the hit in view a `scroll-margin-top` of 130 px (180 px in focus reading), so it comes to rest clear of the bar and not under it. Enter goes to the next hit, on whatever page it is, and starts again at the first after the last; Shift+Enter goes back. Esc, the Close button or the Find button shuts the bar, sends `findbarclose` (which removes the marks) and returns the focus to the document; opening it again with words still in the field searches for them again from the page in view. In focus reading the bar stands 56 px from the top, clear of the place the title row comes to, and Esc closes it before it leaves focus reading. The buttons do not take the focus.

**Marks beside the scroll bar.** `ticks.js` draws a canvas 8 px wide over the scroll bar's track (between its arrows) with a mark for every hit, 3 px high in pink and the hit in view 5 px high in yellow. A mark stands at the place of its hit in the whole document: the page's top and height are read from the page's element, which has its size before the page is drawn, and the place on the page is the hit's offset in the page's text over the length of that text, which follows a page from top to bottom closely enough for the mark to land on the right screen. The strip is redrawn once a frame after the counts, the zoom, the layout or the window change. It does not take the pointer, so the scroll bar underneath works as before.

**The list of hits.** The Search tab of the panel on the right (see The panel on the right). The find bar's list button (**Show all results**, pressed while the Search tab is showing) opens and shuts the panel on that tab, and a search opens it by itself: a new question, or Match case or Whole words, shows the hits there. With nothing typed it says `Type in the search bar to see the hits here` under a search icon in a circle, the same empty look as the Links tab. Closing the bar shuts the panel if it is on the Search tab, and leaves it alone on the Links tab. The count (`4 results`) stands in the heading row above the list at the left, where the rows' words do. The hits stand under a heading for each page that has any (`PAGE 3` in small capitals, its count at the right), and a row is about a hundred characters round the hit, cut at whole words, with the hit itself marked and an ellipsis where the text goes on. Each row still holds its page for a screen reader (`.pg`, drawn nowhere). The row of the hit in view is raised like a chosen tab (the bar colour, a hairline and a soft shadow) with its hit in yellow, and the list scrolls to keep it in view as Enter steps on. A click on a row goes to that hit: its page, the hit in yellow, the count, and Enter and Shift+Enter carry on from it. The list is virtual: a heading is 30 px and a row 52 px, `hits.pages()` in `search.js` gives each page's first hit and count, the list is as tall as the headings and rows together, and only the headings and rows in view and three rows either side exist, so hundreds of thousands of hits cost what a dozen do. The text of a page is read by `getTextContent` when the first of its rows is built, and the last 60 pages' texts are kept. A new question empties the list and starts it again; closing the bar empties the marks. pdf.js finds page after page, so while it works the hit a row stands for can change from one moment to the next (the pages before the one in view are done last); each row keeps a key of its page, its place in the page, its offset and its length, and is drawn again whenever the key changes, so a row never shows the hit of an earlier, shorter question.

pdf.js has no call to go to a given hit. The list and the marks read the controller's `pageMatches`, `pageMatchesLength`, `selected` and `_pageContents`, and a click on a row sets `selected`, `_offset` and `_scrollMatches` and sends `updatetextlayermatches`, which is what the controller does when it steps to a hit. All of it is in `search.js`; `pdfjs-dist` is pinned, and a test goes through each of these.

## Links

A link inside a page goes where it points: pdf.js's own link service scrolls to the destination, and runs the actions it knows (next, previous, first and last page, back and forward). A bookmark in the Outline tab and a click on a link both go through the same service, so both leave a place to go back to. **Alt+Left** goes back and **Alt+Right** forward, through pdf.js's `PDFHistory` (`viewer.js`), which keeps a place per followed link in the page's own session history and never goes beyond the first or the last; there is no button for them, and the keys are ignored while a text field has the focus.

Web links are drawn blue: their layer (`.annotationLayer`) lightens what is under it, so dark text turns blue and white paper stays white, and pdf.js's yellow hover is not shown. A link inside the document (pdf.js marks its element `data-internal-link`: a contents entry, a cross reference, a named action) keeps its text as it is; lightening can only show a colour on dark text, so a hover or focus mark on those would not show on white paper. A page with form fields is left as it is, because lightening would hide the text typed in them. A link to an address never carries the address: `viewer.js` replaces the link service's `addLinkAttributes`, so the link in the page has an empty `href` and its tooltip is the address. A click asks the main process with `pdfws:check-link` what the address reads as and shows nothing at all when the answer is `null`. Otherwise `dialogs.js` shows a card, **Open this link?**, with the whole address as the URL parser reads it (a name and password in it, and a host in another alphabet in its `xn--` form, are shown) in a box that holds to 96 px and scrolls with a thin scroll bar of its own (`::-webkit-scrollbar` in `workspace.css`, no arrows), a **Copy link** icon button inside the box at its top right (clear of the scroll bar, with room kept for it in the text) and **Cancel** and **Open** below. The copy button asks the main process (`pdfws:copy-link`, which writes the clipboard only for an address `linkTarget` accepts, because the window's session refuses the page's own clipboard permission) and a **Copied** tip rises above it for 1.4 s. The focus starts on Open, Tab stays inside the card, Esc and Cancel close it and return the keys to the document.

While a card is up (this one and the password card) everything round it is `inert`, so nothing behind it can be clicked, selected or scrolled, and `keys.js` and Ctrl with the wheel ignore their keys and turns (Esc still closes the card). A click on the veil leaves the focus in the card. Elements that were already inert, such as a folded dock, stay so when the card goes. Only **Open** sends `pdfws:open-link`, and the main process checks the address again before it calls `shell.openExternal`. `links.js` is that check: `new URL`, and only `http:`, `https:` and `mailto:` pass, so `file:`, `javascript:`, `data:`, `ftp:`, `tel:`, program names, paths and anything over 8 192 characters do nothing. pdf.js itself draws no link for a file, a script, another document or a program, so those never reach the card; the check stands for the ones it does draw and for anything the page is given. If Windows has nothing to open the address with, the corner notice says so. An address is never logged.

## The panel on the right

A panel 300 px wide on the right with two tabs, **Search** and **Links**, as the left panel has Pages and Outline. `side.js` owns it: it slides open and shut (its content keeps to the panel's right edge, so it comes in with the panel rather than being uncovered from the left), switches the tab (an `aria-checked` radio pair, the view that is not showing is `hidden`) and tells each view whether it is on show; a tab switch slides the chosen tab's pill across (one `::before` on `.seg3`, placed by `:has()` on the checked tab) and slides the new view in from the side of the tab it came from over 0.3 s (`data-turn` on the panel, `next` or `prev`); opening the panel does not. The Pages panel switches its tabs the same way. Both views start with the same 32 px heading row: the count at the left, where the rows' words start, and the view's actions at the right. The document area gives up the room, and in focus reading the panel floats over the right edge and the pages do not move. A close button (**Hide panel**) stands beside the tabs, and Esc with the focus in the panel shuts it and returns the keys to the document.

The tabs and the find bar go together. Choosing the **Search** tab turns the floating find bar on (`workspaceSearch.reveal()`) with the focus in its field and the last search in it, all selected, so typing at once replaces it and what is left is searched for again; a search, by typing or by Match case or Whole words, opens the panel on the Search tab, from whichever tab it was on. Choosing the **Links** tab, or pressing the Links button, closes the bar (`conceal()`, which sends `findbarclose` as the bar's own close does, so the hits are no longer marked on the pages) but the field keeps what was typed. Ctrl+F or the Find button while the panel is on the Links tab brings the Search tab with it. The find bar works as it did otherwise: it is the same bar. The **Links** button in the title row (a chain icon, **Links in this document**, the third after Pages and Find) opens the panel on the Links tab, switches to Links when the panel is on Search and shuts the panel when it is already on Links. Nothing about the panel is remembered.

### Links

`linklist.js` lists every web and mail address in the document. Nothing is read until the tab is first shown. It then reads the pages one after the other, with a pause between two so the window stays quick: from each page the Link annotations that carry an `http:`, `https:` or `mailto:` address (pdf.js's `getAnnotations`, so a link to a file, a script or another page is not listed), then web addresses written in the page's text that no link covers (a regular expression over the page's text; an address that breaks over two lines is cut at the break, and trailing punctuation is dropped). A thin line under the heading row fills as the pages are read (its tooltip says `Reading page 4 of 12`), the count (`4 links`) grows beside it and rows appear as they are found; with none found yet the list says `Looking for links…`. The list is in reading order, page by page and top to bottom. An address that occurs again is not listed again: its row says `Page 1 · 2 places` and goes to its first place.

A row is an icon for the kind of address (a globe for a web page, an envelope for a mail address), the address (the host or mail address in bold, the rest of the path after it in grey, cut with an ellipsis, the whole address in the tooltip), the page, and an arrow that shows when the pointer is over the row. The icon turns into the row's selection circle when the pointer is over the row, and every row shows its circle while anything is selected. The circle selects the row. A click on the row goes to the link and lights it: pdf.js scrolls the page to it (`scrollPageIntoView`) and a box in the yellow of the search's hit in view (`--found-now` at 60 %, `.linkhit`) is put over the link, in the page's element, and the keys return to the document. The row is raised as the current one (`.now`, `aria-current`), as a search's current hit is. The box and the raised row stay until another row is chosen, the panel is shut or pdf.js draws the page again (a zoom). A page that is not drawn yet is lit once it is, because pdf.js clears what it did not put in a page when it draws it. The arrow asks to open the address in the same card a link in the page uses (**Open this link?**), so an address is only ever opened by the main process after `linkTarget` has accepted it.

In the heading row, a circle in line with the rows' circles selects every row (tooltip **Select All**); with some rows selected it shows a minus and with all a tick, and it then clears the selection (tooltip **Clear**; `role=checkbox`, `aria-checked` `false`, `mixed` or `true`). The count stands beside it and one copy button at the right. It is grey and reads **Copy** while nothing is selected. With some rows selected it reads **Copy 3**, with every row selected **Copy All**, and it puts the selected addresses on the clipboard one to a line, in the order of the list, and says **Copied** for 1.4 s. The copy goes to the main process (`pdfws:copy-links`, an array; it keeps only what `linkTarget` accepts, each once, writes the clipboard and answers how many it wrote, 0 for anything that is not an array or has over 100 000 entries). A document with none says **No links in this document** and shows no circle and no copy button.

From the keyboard each row is one Tab stop: Up and Down move between rows, Enter goes to the link, Space selects the row, Ctrl+Enter asks to open it and Esc shuts the panel. Rows are `content-visibility: auto`, so a document with thousands of links draws only the rows in view. Every address goes in with `textContent`.

## The Document panel

`ui/properties.js` is a panel 312 px wide on the right, opened by the info button at the right of the title row (**Document info (Ctrl+D)**), by Ctrl+D, or by a click on the file's name, which opens it with the name ready to type over. It shares the right edge with the Search and Links panel: opening one shuts the other (`workspaceSide.onchange` and `shutTab`), and Esc with the focus inside it shuts it. It has up to five cards, and everything from a file goes in with `textContent`.

- **File.** The name without its extension in a field with the extension beside it. A **Rename** button shows in the field once the typed name differs from the file's; it and Enter both rename the file, leaving the field keeps what was typed, and Esc puts the old name back. The main process does the rename (`pdfws:rename`, `rename(token, name)` in `documents.js`): it keeps the extension, refuses a name Windows cannot hold (a reserved device name, a character `<>:"/\|?*`, a control character, a trailing dot or space, over 200 characters), a name another open tab has and a file already there, and never replaces anything. A refusal comes back as `invalid`, `open`, `exists`, `in-use` (the file is held by another program) or `changed` (the file is gone), and the page says it in words under the field. A renamed document keeps its tab, its revisions and its undo history. Below the field are the place (the last two folders, from `pdfws:details`; the page is never given a path), the size and the date the file was changed. The place wraps beside **Show** in up to three lines. When it needs more, the outer folder gets one line, cut with an ellipsis, and the folder that holds the file the other two (`fitPlace`, measured once the card is in the panel), so a long path cannot make the card grow and a long outer folder cannot hide the one that matters; the tooltip has both. **Show** asks Explorer for the file (`pdfws:show`). Every card uses one grid: a 76 px label column and the values in a column of their own, rows 28 px high so a label is level with its field, with more air between the Description fields. The text in a field starts at the same left edge as the values in the other cards, and a field's bottom edge is darker than its other sides (`--field-edge`, at least 3:1 against the field and the card) so it reads as a field. Card headings and the extension beside the name use `--muted`, which keeps them above 4.5:1 on the card in both themes.

The facts are asked for when a tab is shown, before the panel is opened, and kept until the pages or the revision change (`load` in `properties.js`), so opening the panel is usually quick; the cards then arrive together. When they take longer than 300 ms, a moving line under the heading says the panel is loading.
- **Description.** Title, Author, Subject and Keywords as fields, as the PDF engine reads them, or from pdf.js's `getMetadata` without it. A change on leaving a field is the operation `meta.set` (`ops.js`: four texts of at most 1 000 characters, no NUL; `python/pdf_ops/meta.py`), so it is a revision with its own undo, Save and unsaved mark, and an empty text removes that entry. The helper appends it to the file, so the pages are not read again (`reload` is false when every operation is `meta.set` and the save was incremental). The card itself is kept while the panel is drawn again for the new revision, so text typed in the next field and the focus stay where they are. A refused change puts the old text back in the fields it touched, and Esc in a field puts back its saved text and leaves it. Without the PDF engine the card is read only and says **Not set**, in the muted colour, for an empty entry.
- **Document, Security and Fonts.** From `python/pdf_info.py <file> <out.json> properties` (`pdfws:properties`), which the main process runs on the revision on show and remembers until the revision changes. Pages, page size (a paper name when it matches A3, A4, A5, Letter or Legal to a millimetre, **Varies** when pages differ), PDF version, created date and the program that made the file; whether a password is set, which permissions the file refuses, and the signatures; the number of fonts and how many are not embedded, with the list folded away. Without the engine these cards are left out.

Signatures are facts about the file and nothing more. For each signature field the panel says who the file claims signed it, when, whether the signed part still ends where the file did, a certification level, the fields a signature locks and whether bytes follow the last signed part, and it ends with **Pomelo does not check signatures**. It never says a signature is valid. `python/pdf_info.py` walks the form's field tree, reads each `ByteRange` and the `%%EOF` markers, and takes the certification from the `DocMDP` reference of the signature. A file with several signatures cannot tell a later signature from a change after the first, so **Changed after signing** is a statement about bytes after the last signed range only.

## The Pages grid

The **Pages** button in the dock (`pages` icon, **Pages (P)**; its name shows beside the icon in a dock lying flat and only the icon in a column) and the **P** key show a grid of every page in place of the reading view. `organise.js` builds it when it is first asked for: a `.pgrid` listbox (`aria-multiselectable`) with one `.cell` for each page, each a sheet 160 px wide (`--size` on `.cells`; the dock's zoom steps it through 120, 160, 200 and 240 px and `thumbs.setWidth` draws them again at that width) whose height comes from the page's own shape (`--r`), with its number under it. While it is up the reading view is `visibility: hidden` (so pdf.js keeps its place), the marks beside the scroll bar are hidden and `body.tooling` keeps the dock showing in focus reading. P, **Esc** (bound before `focus.js`, so it leaves the grid before it leaves focus reading) and a second press of the button go back, and so does choosing another tab; the keys then return to the document.

The thumbnails come from `thumbs.js`, with a queue and bitmap cache of their own at the grid's width, released when the grid goes or the width changes; an `IntersectionObserver` with 400 px of margin asks only for the cells near the view, so 3 000 pages make 3 000 cells and a few dozen canvases. The selection is a set of page numbers. A click selects one page, **Ctrl** and a click adds or removes one, **Shift** and a click selects from the page last clicked, **Ctrl+Shift** adds that range, **Ctrl+A** selects all, and a press on empty paper starts a rubber band: the cells' boxes are read once, the band scrolls the grid at the edges, **Ctrl** or **Shift** keeps what was selected and a plain click on empty paper clears it. From the keyboard one cell is the Tab stop; the arrows move by a cell or a row (the number across is read from the layout), **Shift** with an arrow extends from where the range began, **Home** and **End** go to the ends, **Space** toggles the focused page, and **Enter** or a double click returns to reading at that page. A selected page has one accent ring (the cell itself draws none, though the window's general focus ring would add a second box round the page and its number) and a bold accent number, a page under the pointer a thinner grey ring, so the states differ without colour alone; the ring is at least 3:1 and the number at least 4.5:1 against the area in both themes, and the hover ring at least 1.5:1 against both the area and the selection ring, which the shot test measures. The focused cell from the keyboard has a ring in the text colour 7 px outside the sheet, so it shows on a selected page too. A bar (`.optbar`, in `.well`) holds the buttons below and the count: above the dock when it lies at the bottom, below it at the top, and in the middle of the bottom edge when the dock is a column. The count reads `N selected`, or `No pages selected` in the muted text colour, in a box of fixed width (116 px) so the buttons after it never move. The well is a size container: under 700 px the bar keeps only its icons (their names stay as tooltips and labels), under 440 px it drops the count too, and it wraps rather than run off the edge. It is hidden while the dock is folded or dragged. While the engine works the pages fade to 55 % after 0.4 s, so a quick change does not flicker, and the list carries `aria-busy`.

Editing needs the PDF engine, so the button asks first (`pdfws:engine`, which answers `hasPdfEngine()`; the app hands in `conversion.getEngines().pdf`). With no engine the button carries a small dot and opens one card, **Editing needs the PDF engine**, in `dialogs.js`: `A one-time download. It runs on this PC and works offline.`, **Not now** and **Install**. **Install** calls `pdfws:install-engine`, which runs the same installer as Settings (`engineSetup`, key `pdf`) and sends its progress as `pdfws:install-note` with that key; the card shows it on a moving line while both buttons rest, ignores Esc, says why in the card when it fails and offers **Retry**. When it succeeds the card closes and the grid opens with no restart. **Not now** or Esc leaves the window as it was. Selecting changes nothing in the document.

### Turning, deleting and moving pages

The bar holds **Add** (a menu, below), **Split…** (below), then a hint, `Select pages to turn, delete or extract`, and **Undo (Ctrl+Z)** and **Redo (Ctrl+Y)**. While pages are selected the hint gives way to a chip naming them (`2 pages`; a press clears the selection, tooltip **Clear the selection**) and **Rotate left**, **Rotate right**, **Extract** (below) and **Delete (Del)**. The hint and the selection's group share one grid cell, the one not in use kept hidden there, so the bar keeps its width and Undo and Redo stay under the pointer as pages are selected; below 700 px the bar keeps only icons and drops the hint, and below 440 px the chip shows only the number. Undo and redo are off at the ends of the document's revisions (`canUndo` and `canRedo` come with the document's state, from `revisions.js`). Each action is one `pdfws:apply` (`pages.rotate` by 270 or 90, `pages.delete`, `pages.move`) or `pdfws:undo` / `pdfws:redo`, so it becomes a revision, shows the dot and the Save button, and can be undone. The grid shows the result at once and does not redraw: turned pages turn on the spot (each shrunk to fit its cell until the picture of it turned is drawn), deleted pages fade while the ones after them close up, and moved pages take the place of the hole. While the engine works the grid is marked busy (clicks and drags on the pages are ignored) and the bar keeps its look: a press on Rotate or Delete is ignored, a press on Undo or Redo waits its turn (up to 20) and runs when the last change has been read back, so a run of presses steps back once for each and stops where there is nothing more to undo. The main process then sends `pdfws:changed` with `reload`, `workspace.js` opens the new revision, and on `pagesinit` `organise.js` keeps the cells it has (`reconcile()` in `show()`): it adds or removes cells at the end if the count differs, numbers them again and draws every cell in view again from the new revision, each old picture staying until its replacement is ready, so nothing blanks. Cells that change shape (a turned page) glide to their new places when their picture arrives. The selection and the focus are the ones the action says (`pending`): turned pages stay selected, a moved page stays selected where it landed, deleted pages leave none. A change that does not happen builds the grid again from the document as it was (`rebuild()`). Undo and Redo change no cells themselves: the same `reconcile()` draws the other version in the same cells. Movement uses the Web Animations API (`translate` for the glide, `transform` for the shake) and is left out when the system asks for reduced motion. `workspace.js` gives the grid the tab on show with `workspaceOrganise.use(tab)` so the bar knows its document.

**Delete** (the button or the Delete key) on every page opens a card, **A PDF needs at least one page**, with **OK**, and sends nothing; the helper refuses it too. **Moving.** Pressing a page and pulling past 4 px takes the selected pages with it, or only that page if it is not selected (a press with Ctrl or Shift is a selection, not a pull). The pulled pages leave the grid, a copy of the page pressed (with the others behind it and their count) follows the pointer, and the other pages move aside, shaking a little from side to side as they go, to open a dashed space, **Drop here**, where the pages will go: in front of the page under the pointer, or after it when the pointer is in its right half. The cells are never renumbered during a pull, so a cancelled one only unhides them. Letting go sends `pages.move` with the pulled pages and the number of the page they go in front of (one past the last page is the end); the pages keep their order, and a drop that would change nothing (a block dropped on itself or next to itself) sends nothing. The list scrolls on by itself when the pointer is within 28 px of its top or bottom edge, as it does for the rubber band (both use `track()`). **Esc** in the middle of a pull puts the pages down where they were. From the keyboard, **Ctrl+Shift+Left** and **Ctrl+Shift+Right** move the selected pages (or the focused one) a place, and **Ctrl+Shift+Home** and **Ctrl+Shift+End** to the start or the end, with the same `pages.move`. A change that does not happen leaves the grid as it was: the engine failing says **Can't make this change** in the corner, a missing engine opens the engine card, and a file that another program changed asks to reload it.

`python/pdf_ops/pages.py` `move(pages, before)` puts each page, in document order, in front of the first page from `before` on that is not moving, with PyMuPDF's `move_page`, so links and bookmarks follow their pages and the result is appended to the file (a `direct` operation). 1 000 of 3 000 pages turned, moved or deleted each take well under a second in the helper; `edit-helper` times them against a 6 s limit.

### Inserting and extracting pages

**Add** opens a menu of **Files…** and **Blank page**, with the focus on Files…. A press on the bar leaves the focus in the grid, and a focus moved by script takes on the ring of the one before it, so the menu and the Add files card move it with `focus({ focusVisible })` and show the ring only when they were opened from the keyboard (a click with `detail` 0). A blank page goes after the last selected page, or at the end when none is selected, and is selected when it arrives. **Files…** opens the Add files card (below). Files can also be dropped on the grid (the preload sends a drop on `.pgrid` to `pdfws:drop-sources`, not `pdfws:drop`): they go in front of the page under the pointer, or after it in its right half, or at the end elsewhere in the grid. From the drop until the pages are in, the plus of **Add** turns into a spinner (`adding` in `organise.js`).

The page never holds a path. `pdfws:choose-sources` asks for PDFs, pictures and documents, several at a time (`chooseInsert` in `workspace.window.js`), and gives their paths to the preload, which tells the page how many there are and passes them on to `pdfws:drop-sources`, as it does with a drop. `pdfws:drop-sources` answers `{ id, name, kind, ext, group, locked, pages, needs }` for each usable file among the paths (`kind` is `pdf`, `image` or `document`; `pages` is a PDF's page count, read with pdf-lib up to 50 MB; `needs` is `soffice` when only LibreOffice can make the document into a PDF), or say `Can't add these files` in the corner when none is usable, and `documents.addSource` keeps the id against the path (100 at most; the oldest is forgotten first). `pages.insert` then names the files by id (50 at most, each once), and `documents.apply` turns the ids back into `{ id, file, kind }` for the helper. A document (`kind: 'document'`: Word, OpenDocument, RTF, text, Markdown, HTML, EPUB, spreadsheets, presentations, whatever `conversion.asPdf` finds a route to PDF for) is first made into a PDF with `makePdf`, which the app hands in as `conversion.convertFile(src, 'pdf')`, in a folder of its own in the session folder; the helper reads that PDF in its place as `kind: 'pdf'`, and the folder is removed when the change ends, whether it was made or not. A document dropped on the grid that needs LibreOffice opens the Add files card instead, which offers to install it. A protected PDF asks for its password in the same card as an opened file, with the PDF's name under the title (`askPassword(wrong, abort, name)`; the card for the document in the window has no name line), and `pdfws:unlock-source` checks the password with `checkPassword`, handed in by the app with `probeLocked`; the password stays in memory, goes to the helper on its standard input in a `sources` map keyed by id, and is zeroed when the change ends. Cancelling the card inserts nothing.

`python/pdf_ops/pages.py` `insert` opens each PDF and puts its pages in with PyMuPDF's `insert_pdf`, which keeps links and form fields; a picture is a page of its own size, shrunk to fit 842 points on its long side. `blank` is a page the size of the page before it, or of the first page when it goes first. Both are `new` operations, so they are appended to the file, and the helper reports the number of pages each one added (`{"added": [...]}`) so that `ops.arrange` can tell the new pages from the old ones and a change followed by its undo leaves nothing to save.

**Extract** asks for a file name (**Extract a page** or **Extract pages**, suggesting `<name> (pages 2-3).pdf` beside the document) and writes the selected pages to it with `pages.extract`, an `output` operation: the helper writes a new file, `documents.extract` moves it into place, and the document, its revisions and its selection stay as they were. The corner notice says **Page extracted** or **Pages extracted**. A protected document gives a protected file with the same settings.

Pages that were not in the file when the document was opened, or last saved, wear an **Added** tag in the grid: a pill straddling the top edge of the sheet at its left, in the accent's strong tone with white text (dark text in the dark theme), so it reads at 4.5:1 and does not depend on colour alone, and the cell's label says `Page 5, added`. The state sent to the page (`pdfws:changed` and the answers that carry it) lists them as `added`, read from the revision's `layout` (a page whose origin is 0); `organise.js` tags the cells from it whenever the grid is built or its pages are read again. Undoing back to the file as opened, or deleting the new pages, takes the tags away, and so does a Save over the file: `markSaved` in `revisions.js` makes the saved revision its own base with no layout, so the pages it holds are no longer new and later changes are counted from it (`organise.js` reads the state again through `use`, so the open grid loses its tags at once). A copy saved to another name does not clear them, because it closes the document.

### Splitting and adding files

**Split…** opens a card (`ui/split.js`) with a switch, **By ranges**, **Every N pages** and **At bookmarks**, a field and **Cancel** and **Split**; the files are saved next to the document. By ranges takes `1-3, 4-9, 10-` (a page, a range, or a range open at the end; each makes one file). Every N pages makes a file for each N pages, the last one shorter. At bookmarks makes a file for each top-level bookmark that has a page of its own (the page reads them from pdf.js, which has the destinations, and sends the pages), and the first file begins at page 1; the card counts the files (`3 files, one for each top-level bookmark.`) or says `No bookmarks to split at.` and leaves **Split** off. One line under the field (`split-note`, the field's `aria-describedby`) says what to type in each mode (`One file for each range, separated by commas`, `The last file takes the pages left over`), gives an error in its place, and carries the bookmark count, so the card is one height in every mode and its buttons do not move under the pointer. Between the field and that line a strip one row high stands for the document's pages, left to right, with a box for each file in one of six colours over the pages it takes, its pages written in it when it is at least 30 px wide (`1-3`), and the list read out as its label. It is true to scale whatever the length (a file of one page in 500 is a 2 px sliver in its place) and pages no file takes are left empty. The row has no track of its own, so it is blank until there is a file. Boxes fade in as they come and out as they go, and glide when their pages change; text that makes no sense on the way to text that does (`1-3,`) keeps the boxes 400 ms before they go, so typing does not make them blink. It follows what is typed: the page asks `pdfws:split-plan` with the request and its page count, and the main process answers the first and last page of each file from `splitParts`, or nothing when the request makes no sense. The page sends the request as typed, `{ mode, text | n | starts }` with its page count, and the main process turns it into lists of pages in `splitParts` in `ops.js`, the one place that reads ranges: a request that makes no sense is answered `{ stop: 'invalid', message }`, which the card shows under the field (`Use page numbers such as 1-3, 7`, `Use a number of pages such as 5`, or `This document has 12 pages` for a page past the end), and one that would make more than 100 files is refused with `That would make more than 100 files`. `documents.split` writes each list with `pages.extract` in one turn of the document, so every file comes from the same revision and nothing can be undone in between. A file is named `<name> (1-3).pdf`, with `uniquePath` (handed in by the app) choosing another name when that one is taken, so nothing is overwritten; the corner notice says `Split into 3 files` and `Saved next to <name>`. If a file cannot be written (no space, read-only folder), the notice says why as **Can't save** does, and the files made before stay.

**Add files** (`ui/addfiles.js`, from **Add ▾ Files…**) lists the open document and the files to add round it, in the order they will have: the files above the document go in front of its first page and the ones below it at its end, in one `pdfws:apply` of two `pages.insert` (the end first, so the first insert does not move the place of the second), so one Undo takes them all away and their pages wear the Added tag. Each row has a handle (**Drag to move**; Alt+Up and Alt+Down move it from the keyboard), Pomelo's icon for the file's type (`pomeloIcons.draw` from the wheel), the name, a line under it (`3 pages`, `Made into PDF pages`, `Needs LibreOffice`), and **Remove**; the document's row has the **This document** tag and an accent edge, and no Remove. A row dragged by its handle follows the pointer, lifted with a shadow, while the others glide out of its way (Web Animations, left out for reduced motion); the list scrolls when the pointer nears its ends, and Esc puts the rows back. Files come from the dashed button, `Drop PDFs, pictures or documents, or choose files`, or by dropping them anywhere on the card (the preload sends a drop on an element with `data-drops` to the page as `card`): while files are dragged over it the whole card turns into one `Drop here` place, and goes back when the drag leaves it, ends or drops. Until the main process has read the files chosen or dropped, a pulsing row stands in for each (it shows only after 150 ms, so a quick read does not flash) and the buttons wait. **Add to document** keeps the card up with a spinner beside its word, the list dimmed and inert, Cancel and Esc off, until the main process has made the change, so a document that takes a while to convert is seen to be on its way. Files that cannot be added are left out and the card says `Only PDFs, pictures and documents can be added`. A document that needs LibreOffice has an **Install** button, which runs `pdfws:install-engine` with the key `soffice` and shows its progress in the row (`Installing LibreOffice… 40%`); **Add to document** stays off while any row needs it, and a failed install says why under the list. The list shows five whole rows and scrolls past that, with the last row fading while there is more below. A long name loses its middle, so its last 14 characters (a date, "final", the extension) stay in view (the name has `dir="auto"`, so a right-to-left name keeps its start on the right); the full name is the row's tooltip. A protected PDF asks for its password first, over the card (`askSource` in `dialogs.js`), and is left out if the user gives up. 50 files at most can be added at once.

## Select, Highlight, Draw and Text

Five tools stand in the dock before **Pages**: **Select (V)**, **Highlight (H)**, **Draw (D)**, **Text (T)** and **Eraser (E)**. `ui/annotate.js` builds them and `ui/markup-bar.js` holds the parts of their option bar that do not touch pdf.js (the buttons, the groups and the colour palettes). A tool is chosen by its button or key and put down by the same button or key, by **Esc**, or by choosing the Pages grid. While one is in use a second bar (`.optbar`, in `.well`) stands above the dock with that tool's choices. Select and Eraser have no bar. Highlight, Draw and Text show three colours and a fourth button, **More colours**, that opens a panel of 24 (`HIGHLIGHT` and `INK` in `markup-bar.js`; the ink palette has White, and Text uses it too). The panel shuts when a colour is picked, on a press outside it and on **Esc** (which then leaves the tool on). The button shows the colour in use when it is not one of the three. Draw also has Pen and Marker (the chosen thickness times 6, at 40 % opacity) and 1, 2 or 4 pt; Text has Smaller and Larger (6 to 72 pt, 12 by default) and three fonts (Helvetica, Times, Courier, each shown as `Aa` in its own face). The bar steps aside (`opacity: 0`) while a menu of the dock is open, so a menu never lies over it. The drawing is pdf.js's annotation editor, started in `viewer.js` with `annotationEditorMode` set to a mode of the tool in use and `annotationEditorHighlightColors` from `annotate.js` (the first eight colours of the highlight palette, for the picker of a selected highlight). **Undo (Ctrl+Z)**, **Redo (Ctrl+Y)** and **Clear all** are a small group (`.editpill`) that floats in a corner of `.well`: top left, bottom left when the dock is at the top, top right when it is at the left. It is hidden with no document, while the Pages grid is up (which has its own Undo and Redo) and in focus reading unless a tool is in use. Undo and Redo step the editor first and then the revisions already written. Clear all selects every mark the editor holds and deletes them as one editor step, so Undo brings them back; it leaves marks already written to the file alone (Undo takes those back as revisions). A choice in the Draw bar is for the strokes still to come: the stroke being drawn is ended and nothing is selected before the choice is sent, so Pen after Marker does not change what was drawn (`choose()` in `annotate.js`, using the UI manager taken from pdf.js's `editingstateschanged` event). A choice in the Text bar also applies to the selected text box. Over the page the highlighter's pointer is a dot of its colour (`.hdot`, a fixed element that follows the pointer, because the page's content security policy blocks a `data:` cursor); over a word it is pdf.js's text cursor, since a drag there selects the words, and a drag that began on a word keeps that cursor wherever it goes (`body[data-selecting]`). In Highlight a word's box is 8 px wider each side (`workspace.css`), so a press just before a line's first letter starts a text selection from it instead of a free-form highlight. A drag that starts on the dot draws a free-form highlight, and the dot stays under the pointer for all of it. The remove button of a selected mark is drawn by `annotate.js` as an inline icon, because pdf.js paints it as a mask, which shows nothing in this window. The existing annotations of a file are not editable: `viewer.js` makes `AnnotationLayer.prototype.hasEditableAnnotations` answer false, so the editor never takes one over and loses it on save.

Select is pdf.js's stamp mode, which stamps nothing here and so lets a mark be clicked, moved, resized and deleted. Marks answer the pointer only in Select (`body[data-tool]` rules in `workspace.css` set `pointer-events: none` on the editors of the other tools, text boxes excepted in Text), so a drag over a stroke in Draw carries on drawing, and one over a highlight in Highlight carries on highlighting. **Eraser** is the same stamp mode with `body[data-tool="eraser"]`: a press on a mark takes it away and a drag takes each mark it passes over, through the editor's own `delete` so Undo brings each back (`erase()` and the pointer handlers in `annotate.js`). The pointer is an eraser (`.ecur`, a fixed element that follows the pointer, as `.hdot` does) and the mark under it is outlined. A mark is hit by its box, so a diagonal stroke is erased from anywhere in its box. pdf.js's floating toolbar of a highlight (a colour menu and a bin) is hidden in `workspace.css`; Delete and Eraser take its place. Only Select picks a mark up: in Highlight the `editingstateschanged` handler lets go of whatever pdf.js selected (the highlight just made), and `workspace.css` draws no outline, handles or toolbar on a selected mark in Highlight or Draw. pdf.js gives a text highlight an `.internal` box that takes the pointer whatever its editor does, so `workspace.css` turns that off outside Select: the pointer then reaches the text under it, the highlighter cursor stays, and a second highlight can be laid over the first. Highlights blend with `multiply`, in the window (pdf.js) and in the file (PyMuPDF's highlight appearance), so two colours mix. A free-form highlight is saved as an ink stroke, which mixes by transparency instead.

What is drawn stays in the editor and is not a revision yet. It is written when something needs the file: **Save**, **Save a copy**, **Convert to…**, opening the Pages grid and leaving the tab (`flush()`; a text box still being typed is taken in first by putting the tool down; the editor draws nothing for a tab that comes back, so a tab is not left while it holds marks that could not be written). The tab shows the dot and the Save button from the first mark (`tab.edited`), and closing the tab or the window asks about it like any change.

- With the PDF engine, each entry of `annotationStorage.serializable` becomes an `annot.add` operation (`operations()` in `annotate.js`) in one `pdfws:apply`, so the whole flush is one revision with one Undo. pdf.js's own `saveDocument()` and `getData()` are never called, so a 100 MB file costs no copy in the renderer. A refusal says **Can't save this markup** with the reason and leaves the marks in the editor.
- Without the engine, `saveDocument()` writes the file and `pdfws:put-revision` takes it, up to `NO_ENGINE_SAVE_LIMIT` (100 MB). A larger file opens the engine card with the heading `Saving changes to a file this large needs the PDF engine.` and writes nothing. `pdfws:state` carries the limit as `saveLimit`.

`annot.add` (`ops.js`, `python/pdf_ops/annots.py`; kind `annotate`, saved by appending to the file) takes `type` (`highlight`, `ink` or `freetext`), `page`, `color` (three whole numbers) and, by type: `quads` (8 numbers each) for a highlight; `paths` (strokes of x, y pairs) and `thickness` for ink; `rect`, `text` (1 to 5 000 characters), `size` and `font` (`Helvetica`, `Times` or `Courier`, written as PyMuPDF's `helv`, `tiro` and `cour`) for a text box; `opacity` is optional. The page sends points of the page as it is shown, counted from the top left (`PageViewport.convertToViewportPoint`); the helper turns them into the page's own frame with PyMuPDF's `derotation_matrix`, so a turned page, a media box that does not start at 0, 0 and a crop box all land where they were drawn. A highlight is made from the bounding box of each quad. A text box is turned with the page so it reads upright. A free-form highlight has no words under it, so it is sent as an `ink` stroke with the colour, opacity and thickness it was drawn with. A mark is limited to 5 000 quads or strokes and 500 000 coordinates, in the schema and again in the helper.

## Converting

The **More** button (three dots) stands after the place for the tools. Its menu opens above the bar, like the View menu (opening one closes the other, Esc closes it, Up and Down move between the items) and holds **Convert to…** and **Save a copy** with its shortcut, Ctrl+Shift+S, which is the same action as the key.

**Convert to…** asks the main process what the wheel would offer for the document's file (`pdfws:convert-targets`, from the conversion feature's `targetsFor`, handed in by the app) and opens a card, **Convert to**, with a button for each format (the format's file icon from `src/ui-shared/wheel-icons.js` with its name below, up to eight, in the wheel's order) and Cancel. A file the wheel has nothing for gets the wheel's own explanation in the corner of the screen and no card. A choice goes to `pdfws:convert(token, to)`, which starts the same job a drop on the wheel starts, and its progress, cancel and result are in the corner of the screen as for any conversion. The main process starts a job only for a format `targetsFor` lists for that file.

The converter reads the file on disk. A document with changes first asks **Save your changes before converting?** with Cancel, Save a copy and Save. Save is the Save button (it asks **Replace the original?** the first time) and the file saved is converted; Save a copy is Ctrl+Shift+S and the copy, which opens in place of the document, is converted. Cancel at either card converts nothing. The window gives the converter no password, so a protected file is converted as the wheel converts one dropped without it.

## Page colours and the remembered view

**Page colour** is the last group of the View menu. **Original** draws the pages as the file has them. **Sepia** (paper `#f4ecd8`, text `#4b3b25`) and **Dark** (paper `#1e1e20`, text `#d8d8dc`) and **Custom colours…** draw them through pdf.js's `pageColors`, a pair of colours it maps the page's colours between (black becomes the text colour, white the paper colour, the greys in between), so the file is not changed. `colours.js` hands pdf.js the pair when the viewer is made and, when the user chooses another, sets `pageColors` on the viewer and on every page view and calls `viewer.refresh()`, which draws the pages again with their text and links kept. `--page-bg-color` on the viewer element is the colour an undrawn page shows, so a dark page does not flash white while it loads. The thumbnails in the Pages panel are the file's own colours. The menu puts a tick on the choice in use.

**Pictures keep their colours.** pdf.js applies `pageColors` as one filter over the finished canvas, so it cannot leave a picture out. When colours are on, `colours.js` therefore draws a second layer for every page that has a picture, over the first inside the page's `.canvasWrapper`: the page is drawn again in the file's own colours on a see-through canvas, once with only the picture operators (pdf.js's `operationsFilter`, keeping the operators that set the matrix, clip, groups and hidden layers, and every `constructPath` that ends a clip) and once whole, and the whole page is cut to the opacity of the first (`destination-in`). What is left is each picture as the file draws it, text and shapes that stand over it included, and nothing else: the see-through part of a picture shows the page's paper and a picture cut by a clip stays cut. A page with no picture operator gets no layer (`getOperatorList` is read to tell). The layer is made when pdf.js has drawn the page (`pagerendered`), so a picture shows in the page's colours for a moment first; it follows a zoom by taking the size of the page's own canvas, and it is removed when the choice goes back to Original.

**Custom colours…** opens a card (**Page colours**) with a row of five swatches for the page and one for the text, **Cancel** and **Apply**. The card starts on the pair in use, or on cream and dark grey. Left and Right (and Up and Down) move through a row's swatches, Esc and Cancel change nothing, and Apply draws the pages and returns the keys to the document. Like the other cards it makes everything behind it `inert`.

Web links are blue on a light page. On a page whose colour is dark (`colours.js` finds the paper's luminance and puts the class `dim` on the viewer element) the links' layer darkens instead of lightening and its blue is a light one (`#8ab4f8`), so the text of a link is light blue and the paper under it is left as it is.

**The remembered view.** The page keeps these in `pdfView` beside `window` and `dock`: `zoom` (`page-fit`, `page-width` or a number from 0.1 to 10), `layout` (`continuous` or `spread`), `sidebar` (`{ open, tab: 'pages' | 'outline', width: 214 to 320 }`) and `pageColours` (`original`, `sepia`, `dark` or `{ page, text }` as `#rrggbb`). A change is sent to the main process with `pdfws:view` 300 ms after the user stops changing things (`remember` in `viewer.js`), and the page starts from the view `pdfws:state` returns. A window records nothing until it has restored the view it was given, so opening a file does not write what it has just read. `view.js` is the one place the values are checked, in the main process: `cleanView` keeps a field only when it is valid and drops the rest, both in what the page sends and in what the settings file holds when the page starts; a colour is valid only as `#` and six hexadecimal digits, and `window` and `dock` are not view fields, so they can be written only by their own code. A value that is already stored is not written again.

## Focus reading

The button at the right of the title row, or F11, asks the main process for full screen with `pdfws:focus`. The window answers with `pdfws:focus-changed` when it enters or leaves, and the page changes only then, so leaving by any other route is followed too. In focus reading the title row slides up and the dock down, a faint handle at the bottom edge hints at the dock, the zoom becomes Fit page and the zoom the user had is put back when it ends. The title row returns while the pointer is within 56 px of the top, the dock within 120 px of the edge it stands at (a dock at the top stands below the title row); the dock also stays while the focus is inside it. Esc goes through the open card, menu or field first (they use the key and mark it handled) and leaves focus reading last. The window's size and place are not stored while it is full screen.

Keys are ignored while a text field has the focus, apart from Ctrl combinations and F11. The listener is on `window` so a card that closes itself on Esc has used the key first.

## Comments

A comment is a Text (note), Highlight, Underline, StrikeOut, Squiggly, Ink, Square, Circle, Line, Polygon, PolyLine, Caret or Stamp annotation with text in its contents. Free text is left out: its contents are what it shows. Each comment becomes a 26 x 24 px marker 10 px outside the page, level with the first box it covers, never closer than 28 px to the one above. Position and size are kept as fractions of the page, so a zoom moves them without being worked out again. On the left page of a two-page view the markers are on its left; with under 46 px beside the page they move 8 px inside its edge. A marker opens a 240 px card (author and date when the file has them, then the text) and lights what it is about: a wash and underline on commented text, a ring on a note, an outline on any other annotation. The card is closed by the marker, a click elsewhere, or Esc. pdf.js's own note icons and popups are hidden in `workspace.css`, so the page shows nothing of a comment. A marker belongs to the page element, so pdf.js removes it with the page's drawing and it is built again when the page is drawn.

The window is frameless with `titleBarStyle: 'hidden'`. The title row is part of the page and Windows draws the minimise, maximise and close buttons over its right-hand end, in colours that follow the theme. On Windows 11 (build 22621 or later) the window has an acrylic background that the wheel's `--plate` colour tints. Before that, or when `createWorkspace` is given `solid: true`, the window is opaque and the page gets the `solid` class (through `?solid=1`) so `src/ui-shared/window.css` paints the title bar colour of Settings. `workspace.window.js` calls `createAppWindow` in `src/shared/electron/windows.js`, which makes the window, its offline session and its saved place, and adds only the full-screen events the page listens for.

The window's size, place and maximised state are saved in `pdfView.window` of `settings.json` after the user pauses, and when the window closes, with the time (`savedAt`). `src/shared/core/bounds.js` decides where it opens: the saved place if it was saved in the last 24 hours and at least 100 px of its title row is on a screen, otherwise 1200 × 800, not maximised, in the middle of the main screen. A place saved without `savedAt` counts as old. The minimum size is 900 × 600.

## Contracts

- Command line: `--open=<path>`. A relative path starts from the folder the command was run in. A start with this switch opens no Settings window. A running Pomelo gathers the `--open` starts that come within 400 ms of each other, as Explorer makes for a selection, and opens them as tabs, the first in name order on show.
- Explorer: the right-click entry **Open in Pomelo** on `.pdf` files (`SystemFileAssociations\.pdf\shell\PomeloOpen`, written beside **Convert with Pomelo** by `src/app/shell-menu.js` and removed with it) starts `Pomelo.exe "--open=%1"`.
- IPC channels: `pdfws:state`, `pdfws:read`, `pdfws:unlock`, `pdfws:close`, `pdfws:drop`, `pdfws:focus`, `pdfws:dock`, `pdfws:view`, `pdfws:check-link`, `pdfws:open-link`, `pdfws:copy-link`, `pdfws:copy-links`, `pdfws:put-revision`, `pdfws:apply`, `pdfws:undo`, `pdfws:redo`, `pdfws:save`, `pdfws:save-as`, `pdfws:convert-targets`, `pdfws:convert`, `pdfws:choose-sources`, `pdfws:drop-sources`, `pdfws:unlock-source`, `pdfws:extract`, `pdfws:split-plan`, `pdfws:split`, `pdfws:reload`, `pdfws:properties`, `pdfws:details`, `pdfws:rename`, `pdfws:show`, `pdfws:engine` and `pdfws:install-engine` and `pdfws:close-window` (page to main), `pdfws:install-note` (main to page, `{ key, note, fraction }` while an engine installs), `pdfws:changed` (main to page, a document's state) and `pdfws:closing` (main to page, no data), `pdfws:focus-changed` (main to page, a boolean) and `pdfws:opened` (main to page, the documents just opened or shown again, as `{ token, name, size }`). `pdfws:close` takes a token and closes that document, and the window with the last one; `pdfws:drop` takes an array of paths and opens those that are absolute and end in `.pdf`. `pdfws:properties` takes a token and answers what `pdf_info.py` found as `{ facts }`, or `{ stop: 'no-engine' }` or `{ stop: 'failed' }`. `pdfws:details` answers `{ folder, modified }`, `pdfws:rename` takes a token and a name without its extension and answers `{ info }` or `{ stop }`, and `pdfws:show` shows the file in Explorer. `pdfws:engine` answers whether the PDF engine is installed and `pdfws:install-engine` takes `pdf` or `soffice`, refuses anything else, installs that engine and answers `{ ok, message }`. `pdfws:split-plan` takes a split request and a page count and answers `{ spans }` or `{ error }`. `pdfws:focus` takes a boolean; anything but `true` leaves full screen. `pdfws:dock` takes one of the four sides and ignores anything else. `pdfws:view` takes any value; `cleanView` keeps its valid view fields and the main process writes only those that differ from what is stored. `pdfws:state` answers `{ documents, dock, view }`, where `view` has passed through `cleanView` too. `pdfws:check-link` takes any value and answers the address or `null`; `pdfws:open-link` takes any value and opens it only if `linkTarget` accepts it; `pdfws:copy-link` copies it to the clipboard on the same condition; `pdfws:copy-links` takes an array and copies the addresses that pass, one to a line. `pdfws:unlock` takes a token and a password of 1 to 4096 characters and refuses anything else; nothing logs its arguments. `pdfws:read` takes a token and two integers and refuses an unknown token, a non-integer, a negative start, an end past the size of the file and a span over 4 MiB. It reads only from the handle held since the file was opened, so a file replaced or deleted afterwards cannot change what the window shows, and a file cut short is an error, never padding.
- Settings key `pdfRecent`: up to ten full paths of PDFs opened lately, newest first. The main process writes it; the page cannot read it or change it.
- Settings key `pdfView`: `{ window: { x, y, width, height, maximised } | null, dock: 'bottom' | 'top' | 'left' | 'right', zoom, layout, sidebar, pageColours }`, the last four as described in Page colours and the remembered view and all optional. The page asks for a change and the main process writes it after checking it.
- The window's session (the in-memory partition `pomelo-workspace`) cancels every `http`, `https`, `ws`, `wss` and `ftp` request and refuses every permission. The page's Content-Security-Policy is `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; worker-src 'self'`. It does not reach pdf.js's worker, which is why the session also blocks the network.
- pdf.js is the exact version pinned in `package.json` (`6.5.438`), loaded from `node_modules/pdfjs-dist` by file URL. Its cMaps, standard fonts, WASM decoders and colour profiles load from the same folder, and `useWorkerFetch: true` is what lets the worker read them from `file:` URLs.
- Text from a document (its file name, the author and text of a comment) is put in the page with `textContent`.
- The scroll bars of the pages and of the Pages panel are thin thumbs that is transparent until the area scrolls (the `scrolling` class stays 0.9 s after the last scroll) or the pointer is over it.

## Known limits

- A picture becomes one page, and only the first frame of an animated GIF or a multi-page TIFF is used. Pictures are PNG, JPG, GIF, BMP and TIFF. A PDF inserted from a file that is open in another tab is read from its saved file, not from the changes in the tab. The grid's selection is lost when the tab changes. A password-protected file asks for its password again after each change, because the pages are read again from the new revision.
- Ten PDFs at most are open at once. The changes the window makes are the four Description fields, the Pages grid and the markup tools.
- The tools add new marks only. Select reaches the marks that are still in the editor, not the annotations already in a file, and a mark is out of its reach once it is written (on Save, a copy, Convert or the Pages grid). Bold is not offered in a text box. PyMuPDF gives no way to ask whether a font has a glyph, so a character the font lacks is written and drawn as the font draws it, not refused first; Chinese text uses a font that is not embedded in the file, so it shows only where the reader has one.
- A text box is in one of three standard fonts. The fonts embedded in the document are not offered: PyMuPDF writes a text box only in the standard fonts, and an embedded font is usually a subset that lacks the letters a new text needs. Text in a script those fonts do not cover is drawn in a stand-in face chosen by the engine.
- A text box cannot be saved on a page whose user unit is not 1: pdf.js keeps such a box inside the unscaled page, so its rectangle cannot be trusted, and a card says so. Highlights and strokes on those pages are saved. While a tool is in use its bar covers the lower part of a page that fits the window.
- There is no list of recent files to choose from: `pdfRecent` only decides where the Open dialog starts. Tabs have no shortcut, no drag to reorder and no way to open one from inside the window other than a drop.
- A tab not on show keeps its document in memory, so ten large files cost their size each. Search is cleared when the tab changes.
- Reading only: pages scroll, zoom and lay out one or two across. A window starts as the last one was left (zoom, layout, panel, page colours), not as the file was last read: there is no place per file.
- A picture's stencil masks (a scanned page's black-and-white image, a logo drawn as a mask) are painted in the text colour and so are recoloured; only images with their own colours are kept, and one inside an annotation is recoloured. A page with pictures is drawn three times while colours are on.
- Custom colours… offers five swatches for the page and five for the text, not any colour.
- Where a mark stands on its page is estimated from the hit's place in the page's text, so on a page set in columns it can be off by a column.
- Find reads the text layer, so a scanned page with no text has nothing to find, and the count of a very long file grows for a while as pdf.js reads page after page.
- A bookmark that links to a web page or runs an action does nothing.
- The Links tab lists web and mail addresses only, and finds an address written in the text only when it is on one line. A repeated address is one row that goes to its first place.
- A link to another file, a program or a script does nothing. Back and forward have no button, only Alt+Left and Alt+Right.
- Comments are listed only for pages pdf.js has drawn, and cannot be edited or deleted. A reply is shown as a marker of its own.
- Markers are rebuilt when a page is drawn again, so an open comment closes when its page is zoomed.
