# Python helpers

The PDF, OCR and HEIC work that Python does better than JavaScript. Each helper runs as its own process, started by `src/features/conversion/engines/pdf-python` and `heic-python` through `runHelper` (`engine-kit/python.js`); nothing here is linked into the app.

The packages are in `requirements.txt`. The in-app installer, `npm run setup:pdf` (`tools/setup-pdf-engine.ps1`) and `tools/make-notices.js` all read it. PyMuPDF is pinned: its 2.x releases pull in a 120 MB layout-analysis stack that nothing here uses. The code runs on Python 3.9 to 3.13.

## Entry points and libraries

An entry point is run with `python -W ignore <script> <arguments>`. Libraries are imported by entry points and never exit the process.

| File | Kind | What it does |
|---|---|---|
| `pdf_to_docx.py` | entry | PDF to editable Word: `<in.pdf> <out.docx>` |
| `pdf_to_text.py` | entry | PDF to Markdown, HTML or plain text: `<in.pdf> <out> <md\|html\|txt> [images folder]` |
| `pdf_to_tables.py` | entry | The tables of a PDF as JSON for the Excel writer: `<in.pdf> <out.json>` |
| `pdf_to_layout.py` | entry | Text with exact positions, plus background pictures, for the PowerPoint writer: `<in.pdf> <out folder>` |
| `image_to_heic.py` | entry | An image to HEIC: `<in image> <out.heic>` |
| `ocr_warmup.py` | entry | Loads the OCR engine once so its models download during the install |
| `helper.py` | library | `require()`, `progress()`, `exit_no_text()` and `run_pdf_job()` |
| `pdf_ocr.py` | library | Reads scanned pages with RapidOCR into a temporary PDF with real text |
| `pdf_spans.py` | library | What the readers share: `hexcolor`, `BAD_XML`, `TEXT_FLAGS`, `has_unmapped_symbols`, `dominant_size`, `dedupe` |
| `pdf_fonts.py` | library | PostScript font names to Word font families, the fonts Windows has installed (`installed()`), and the installed family closest in width to a font it lacks (`stand_in()`) |
| `pdf_flow/` | library | PDF to Word (see below) |
| `pdf_structure.py` | library | Reading order, headings, lists and tables, written as Markdown, HTML or text |
| `pdf_layout.py` | library | The exact-position reading for PowerPoint |

`pdf_flow/` is the Word converter, split by responsibility: `common.py` (units, escaping, box geometry), `lines.py` (spans to lines, list markers), `shapes.py` (pictures, rules, boxes, tables), `fonts.py` (text measuring), `page.py` (one page), `builder.py` (laying out a region), `lists.py` (numbering), `structure.py` (styles, headers and footers) and `convert.py` (the page loop). Imports only point downwards in that order. `pdf_flow/__init__.py` exports `convert`. A rotated page is read upright (`open_upright`) and written as one text box the size of the shown sheet, turned back (`turned_page` in `builder.py`), so its text stays text and its sheet keeps its size and orientation, the words of a justified line that the PDF stores one by one are joined (`stretched_row` in `lines.py`), the pictures of a page are anchored in its first paragraph or first table cell, and a wide picture at the foot of a page is placed on the page together with its caption (`ends_page` in `convert.py`). Text in the bottom tenth of an upright page, well clear of the rest, and a picture that gridlines cross or that text wraps right up against are placed on the page as well, so Word laying the text a little taller never moves them to a new sheet. A paragraph in a table cell keeps no spare room on its right, and a line that fills its cell is set 1 twip a character narrower, because Word clips what overhangs a cell (`room` and `edge` in `builder.py`). A font Windows does not have is written as an installed serif, sans or mono family of about the same width (`stand_in` and the installed list in `pdf_fonts.py`, used by `FontMeter` in `fonts.py`), and a line Word would set wider than the PDF is condensed by at most 0.8 pt a character (`span_run` in `page.py`). A table row taller than half a sheet may split across sheets (`keep` in `builder.py`). A table drawn as an outer colour with a lighter rectangle inset in each cell is read as one table: the thin strips between the two are not cells (`tables` in `page.py`). The columns of a ruled table are the positions of its rules, not the edges of its fills, because Word draws a shaded cell as a fill the size of the cell and another inset by the cell's padding (`rule_edges` in `page.py`). The gap between a rule and its text is the table's cell padding, and what the cells of a table share (the rule, a shaded header row, stripes, a first column) is written once as a table style, `PDF Table 1` and so on in `styles.xml` (`table_look` in `shapes.py`, `table_style` in `structure.py`), so a cell states only what differs from it, the header row repeats on the next sheet, and Word's Table Design boxes (Header Row, Banded Rows, First Column) and its gallery work on it. The margins are also written on the table, so that they stay when another design is chosen. A cell with nothing in it that is tall enough for a line holds an ordinary empty paragraph, so text typed there shows and the row grows (`blank` in `builder.py`). A centred paragraph gets no first-line or hanging indent. The last letter of a letter-spaced line that fills its cell is a run of its own without the spacing, which Word adds after the last letter and wraps on (`span_run` in `page.py`). Outlined boxes with a gap between them stay separate boxes with four sides, not the rows of one table (`stripes` in `builder.py`), and the edge of an outlined box is not also written as a rule. A number that opens a paragraph whose next line starts under the number, as in `(1) The Supplier ...`, is text, not a list item (`hangs` in `lines.py`). The letter `o` is a bullet only on its own, so a line that starts with `of`, `on`, `or` or `one` keeps that word (`bullet` in `lines.py`). Running text in two or three columns is a continuous section with Word columns, with a column break in a paragraph of its own where the columns end at different heights (`column_runs`, `settle`, `numbered` and `columns` in `builder.py`, `end_sections` in `convert.py`); a large letter beside the first lines of a paragraph is a Word drop capital (`capped` and `drop_cap` in `builder.py`, kept apart from the line beside it by `is_drop_cap` in `lines.py`); a page can therefore hold several sections, `convert_page` returns the header and footer of each, and `attach` in `structure.py` gives references only where they change. A page set freely over pictures and colour is a design page (`page_kind` in `page.py`) and has no flow: `design_page` in `convert.py` renders the page without its text as one picture behind everything and writes each paragraph as a text box anchored to the sheet, in reading order (`text_boxes` and `reading_order` in `builder.py`). A table on a design page is a Word table placed on the sheet (`placed` in `table` in `builder.py`: `tblpPr` anchored to the page, overlap allowed, rows `atLeast`, a single line no taller than the table's shortest row, because Word's own line height for the font can exceed the PDF's row pitch): a ruled table comes from `tables` in `page.py`, three or more rows of text that line up in the same columns with no ruling and that the PDF wrote as one text block come from `aligned_tables`, and the rules and cell colours the table paints itself are taken out of the page picture when `table_art` can tell them from the rest of the drawing, otherwise the page keeps them and the table has no borders or shading. A line ends where the PDF's does unless the paragraph is justified, and a left-aligned box does not wrap, so a wider substitute font cannot break a line; text that is only pixels in a picture stays in the picture. A scanned page, a page stored sideways and a page with no text stay document pages. A line in the top or bottom tenth of the sheet whose text repeats on at least three quarters of the pages, with the numbers that are the page number and the page count read as `PAGE` and `NUMPAGES` fields, is not written in the page: it is a framed paragraph in a header or footer part (`Furniture` in `structure.py`), and a section carries references only where its header or footer differs from the section before it. A header or footer in a table, a box or a design page, and one whose numbers are not the page number, stays where it is. The styles are written by `set_styles` in `structure.py` with no look of their own, so a run states its font and size only where they differ from Normal (`span_run` in `page.py`): a heading is Heading 1 to 3 by its size, the first large heading of the first page is Title, a short bold line of body size on its own above plain text, outside a table or a design page, is Heading 3 (`labels` in `builder.py`), a list item is List Paragraph and a line such as `Figure 1. ...` is Caption (`para_xml` in `builder.py`). A paragraph's lines are `atLeast` the PDF's pitch where Word's own height for the font (`line_height` in `pdf_fonts.py` reads the ascent, descent and line gap from the installed font, which is how Word sizes a line) is no taller, or where the pitch is 1.32 times the size or more, so they make room when the text is made larger (`line_rule` in `builder.py`). They are `exact` where the PDF sets them tighter than the font, where sizes in the paragraph differ by more than 8 %, where the text is not Latin or where the font is not installed. A multiple of the font's height was not used: LibreOffice sizes a line differently and moved the lines. A line that ends at the hyphen of a word the text spells with a hyphen elsewhere keeps it when Word sets the paragraph again (`compound` in `builder.py`). Every drawing id in the document comes from one counter (`Lists.drawing_ids`), so no two pictures or text boxes share an id however many there are on a page. If the sections a page adds ever differ in number from its header and footer states, `convert` pads or trims the states and `attach` puts the header and footer in the first section, and both log it, so the lines taken out of the pages are not lost. `POMELO_DEBUG=1` prints each paragraph's alignment and whether each page is a design page or a document page (`page_kind` in `page.py`).

## How a helper runs

Every entry point starts with `import helper`, then `helper.require(...)` for the packages it needs, then runs `main()` under `if __name__ == "__main__"`. For a PDF, `helper.run_pdf_job(src, work)` does the common part: a scan is read with OCR first (the first 70 % of the progress bar), `work(path, progress)` runs on the PDF, a failure becomes a one-line reason, and the temporary OCR copy is deleted. `work` must close every document it opens before it returns, because Windows will not delete a file that is still open.

## Contracts

The Node side depends on these (`test/integration/python/cli-contract.test.js` checks them):

- Arguments as in the table.
- `POMELO_PROGRESS <0..1>` lines on stdout while it works, and `OK` at the end.
- On failure, one line on stderr and an exit code: 1 failed, 2 a component is not installed, 3 the PDF has no text to convert.
- The messages for a password-protected, a damaged and a page-less PDF, and for a scan when OCR is not installed. The tests assert on them.

## Testing

`node test/run.js --tier=pdf` (needs the PDF engine): the command-line contract, the Word layout checks (`pdf-layout`), and the other formats (`pdf-formats`). For real pages, `npm run test:fidelity` scores PDF to Word against `test/fidelity/baseline.json`; any change to `pdf_flow/` must leave every sample's score equal. `node test/fidelity/run.js --word` does the same comparison with Microsoft Word as the renderer (see `test/README.md`).

## Known limits

- Text in columns is written as Word columns only when it stands in two or three columns with the same gutter, holding lines, inline pictures, tables, boxes, centred captions and equations with their number; anything that crosses a gutter ends the run, and columns beside a rule stay table cells. Columns that end within one and a half lines of each other are left to Word to balance, so text typed at the foot of one runs on into the next; columns that end at different heights keep a column break, and text typed there does not run on.
- A drop capital is a Word drop capital only on a page of running text. On a page set freely over pictures it stays a text box at its place, because Word does not wrap text round a drop capital inside a text box.
- On a design page, a table with no ruling is found only when its rows share one PDF text block and every cell starts at a left edge shared by three lines; a row whose text runs into the next column, or whose first cell was joined to the next one as if it were a list marker, stays a text box and ends the table. Word prints the text of a placed table before the page's text boxes, so a text-order check reads it first. A row added to a table that sits on a coloured panel extends past the panel, and the new row has no panel colour under it. Text turned by anything but a quarter stays in the page picture (a side label turned a quarter is a turned text box).
- Only the text of a header or footer moves into its part: a logo or other picture that repeats on every page stays on each page, and a header or footer that is not the same on most pages, or whose number is not the page number, stays on the page.
- On a document page, chart labels and the labels of small pictures stay inside the picture, so a word count on the printed Word file does not see them.

- The Word and the text/Markdown readers each have their own line pipeline, tuned differently (`dedupe` tolerance 3 versus 4 points, different bullet sets), so their output differs in small ways on purpose.
